# 판정 절차

1단계 졸업 시험에서 4/5 오답이 난 뒤, 재학습으로 만든 절차 3종.

**사례를 외우면 처음 보는 코드에서 막힌다.** 실제로 각 세션에서는 다 맞췄는데 종합 시험에서 무너졌다. 아래는 직관이 아니라 **순서대로 적용하는 절차**다. 헷갈리면 여기로 돌아온다.

세 절차 모두 **재귀**가 핵심이다. 겉만 보면 틀린다.

---

## 1. 이 파일이 클라이언트 번들에 들어가는가

```
1. 이 파일에 'use client' 가 있다               → 들어간다
2. 'use client' 파일이 이 파일을 import 한다     → 들어간다
3. 2에 해당하는 파일이 이 파일을 import 한다     → 들어간다  (끝까지 재귀)
4. 예외 — prop(children 포함)으로 넘어왔다       → 들어가지 않는다
```

> **`'use client'` 에서 시작해 `import` 만 따라 끝까지 내려간 것 전부.**
> **`prop` 은 따라가지 않는다.**

### 이 절차는 "실행 위치 판정기"다

```
번들에 들어간다     =  브라우저로 코드가 간다  =  클라이언트에서 실행
번들에 안 들어간다  =  브라우저에 코드가 없다  =  서버에서만 실행
```

**"번들에 들어가는가"와 "어디서 실행되는가"는 같은 질문이다.**
재시험에서 `TagCloud`(children)는 번들에서 정확히 제외했으면서, 같은 구조의
`Table`은 "클라이언트에서 실행"이라고 답했다. 절차를 목록 만드는 도구로만
익히면 이렇게 갈린다. **어느 쪽으로 묻든 절차 1로 답한다.**

`import` 는 **코드를 가져오는 것**이고 `prop` 은 **결과를 받는 것**이다.
코드는 경계를 넘으면 딸려가고, 결과는 데이터라 그냥 넘어간다.

**주의:** 지시어가 없는 파일은 "서버 파일"이 아니다. 클라이언트가 import 하면
**그냥 클라이언트 컴포넌트가 된다.** `async` 가 아니면 에러도 안 난다 — 조용히
클라이언트에서 실행되고 서버 전용 env 는 빈 값이 된다. 그쪽이 더 위험하다.

**검증 예시**

```
page.tsx      (지시어 없음)  → Header, PostList 를 import
Header.tsx    ('use client') → Avatar, utils/time 을 import      → 1번
Avatar.tsx    (지시어 없음)  → utils/img 를 import               → 2번
utils/img.ts                                                     → 3번 (재귀)
PostList.tsx  (지시어 없음)  → Post 를 import                    → 서버가 import → 제외
Post.tsx      (지시어 없음)  → LikeButton 을 import              → 제외
LikeButton.tsx('use client')                                     → 1번 (방향 무관)
Nav.tsx       (지시어 없음)  → Drawer 에 children 으로 넘어감     → 4번 → 제외
```

## 2. 이 에러를 어느 error.tsx 가 잡는가

먼저 **렌더링 중첩 순서**로 계층도를 그린다. 폴더 구조가 아니다.

```
layout.js → template.js → error.js → loading.js → not-found.js → page.js
바깥 ──────────────────────────────────────────────────────────► 안쪽
```

**이 순서는 외우는 게 아니라 근거로 세운다.**

| 관계 | 근거 |
|---|---|
| `error` 가 `page` 보다 바깥 | page 에러를 잡아야 하니까 (S3에서 확인) |
| `error` 가 같은 폴더 `layout` 보다 안쪽 | layout 이 무너지면 함께 무너졌다 (S3에서 확인) |
| `error` 가 `loading` 보다 바깥 | 로딩 중 터진 에러도 잡아야 하니까 |
| `template` 이 `layout` 과 `error` 사이 | 문서 명시 — *"renders between layout.js and error.js"* |

기억이 안 나면 — **바깥일수록 오래 살고, 안쪽일수록 자주 바뀐다.**
`layout`(네비게이션해도 유지) → `template`(이동마다 재생성) → `error`(사고 대비)
→ `loading`(기다리는 동안만) → `page`(실제 내용).

재시험에서 `template` 과 `error` 를 뒤바꿔 `admin/template` 에러의 판정이 틀렸다.

이 순서를 각 폴더에 적용하며 중첩한다.

```
바깥 ────────────────────────────────────────────────────────► 안쪽
app/layout → app/error(🅰️) → shop/layout → shop/error(🅱️) → cart/error(🅲) → cart/page
```

```
1. 에러를 던진 것의 위치를 계층에서 찾는다
2. 거기서 왼쪽(바깥)으로 이동하며 처음 만나는 error.tsx 를 찾는다
   (자기 자신은 세지 않는다 — 이동한 뒤 만나는 것이어야 한다)
3. 그게 잡는다
```

**검증 예시**

```
cart/page.tsx 에러       → 왼쪽으로 → cart/error(🅲)
shop/layout.tsx 에러     → 왼쪽으로 → app/error(🅰️)     shop/error 는 안쪽이라 함께 무너짐
cart/error.tsx 자신 에러  → 왼쪽으로 → shop/error(🅱️)    자기가 자기를 못 잡는다
```

**함의:** layout 의 에러는 같은 폴더 error.tsx 가 못 잡는다. 부모에 하나 더 둬야 한다.
루트 layout 이 실패하면 갈 곳이 없어서 `global-error.tsx` 가 따로 있다.

## 3. 이 값이 서버 → 클라이언트 경계를 넘는가

```
1. 원시값인가?  (string, number, boolean, null, undefined)      → 넘어간다
2. React 가 아는 내장 타입인가?  (Date, Map, Set, Promise, JSX)  → 넘어간다
3. plain object 또는 배열인가?  → 안의 값들을 각각 1번부터 다시 검사 (재귀)
4. 함수인가?                                                     → 못 넘어간다
5. 클래스 인스턴스인가?                                           → 못 넘어간다

※ 하나라도 실패하면 전체가 실패한다
```

> **바깥 타입이 통과했다고 끝이 아니다. 담긴 것까지 전부 통과해야 한다.**

### 실제 코드에 적용할 때 — 손으로 펼쳐 쓴다

나열된 문제(`a={...} b={...}`)에서는 재귀 검사를 하면서, 실제 JSX 안에 섞여 있으면
겉만 보고 넘어가는 일이 반복됐다. **눈으로 훑으면 prop 최상위만 보인다.**

```
1. prop 이름을 전부 나열한다
2. 값이 배열이나 객체인 prop 은 → 안을 펼쳐서 나열한다   ← 이 단계를 건너뛰게 된다
3. 펼쳐진 목록에서 함수 / 클래스 인스턴스를 찾는다
```

**예시**

```tsx
<Table
  rows={rows}
  columns={[
    { key: 'name', label: '이름' },
    { key: 'price', label: '가격', render: (v) => v.toLocaleString() },
  ]}
/>
```

```
1. rows, columns
2. rows    → [{...}, {...}]              DB 결과. plain object 라 정상
   columns → [ { key, label },
               { key, label, render } ]  ← 펼치니까 보인다
3. render 가 함수 → 실패
```

**주의:** DB 조회 결과를 넘기는 것은 문제가 아니다. plain object 배열이므로
정상 직렬화된다. 오히려 RSC 의 기본 패턴이다. 실패는 **함수와 클래스 인스턴스**에서만
나온다.

기준은 **"서버와 클라이언트가 이미 공유하는 타입인가"** 다.
`Date` 는 양쪽 다 아니까 값만 보내면 복원되고, 커스텀 클래스는 클라이언트가
그 클래스를 모르므로 메서드를 복원할 수 없다.

**데이터는 넘어가고 동작(코드)은 넘어가지 않는다.**

함수의 예외 — `'use server'` 를 붙이면 넘어간다. 단 **함수가 아니라 그것을 가리키는
ID** 가 넘어가는 것이고, 코드는 서버에 남는다 (Server Actions).

**검증 예시**

```
{ user: { name: 'kim', tags: ['a','b'] } }        ✓  끝까지 원시값
{ list: [1, 2, { fn: () => {} }] }                ✗  4번 — 배열 안 객체 안 함수
new Map([['k', new Date()]])                      ✓  Map 도 Date 도 내장
new Map([['k', new (class X {})()]])              ✗  5번 — 담긴 값이 클래스 인스턴스
[{ id: 1 }, { id: 2, render: () => null }]        ✗  4번 — 두 번째 객체 안 함수
```

## 공통 교훈

세 절차 모두 **한 단계 더 들어가야** 정답이 나온다.

| | 겉만 보면 | 실제로는 |
|---|---|---|
| 번들 | `'use client'` 파일만 | import 를 끝까지 따라간 것 전부 |
| 에러 | 같은 폴더 error.tsx | 계층상 바깥의 가장 가까운 것 |
| 직렬화 | 값의 타입 | 담긴 것까지 재귀 검사 |

**"이거 하나만 보면 되겠지" 하는 순간 틀린다.**
