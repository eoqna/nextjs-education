# 오답노트

## 기록 규칙

**멘탈 모델 오류만 적는다.** 오타, API 이름 착각, 단순 실수는 적지 않는다. 여기에 잡동사니가 쌓이면 다시 읽지 않게 된다.

**`[전제]` 필드를 비워두지 않는다.** 틀린 답이 아니라 **틀린 전제**를 고쳐야 재발하지 않는다. 이 줄을 쓰기 어렵다면 아직 왜 틀렸는지 모르는 것이고, 그건 그 자체로 중요한 신호다.

## 태그

| 태그 | 범위 |
|---|---|
| `#rsc경계` | 서버/클라이언트 구분, `'use client'`, 직렬화, 컴포지션 |
| `#프리렌더` | 정적 셸, PPR, Suspense 경계, `connection()` |
| `#캐싱` | `use cache`, `cacheLife`, 무효화 3종 |
| `#서버실행` | Route Handlers, Server Actions, 쿠키/헤더, proxy |
| `#라우팅` | 파일 규약, 중첩, 동적 세그먼트, 네비게이션 |
| `#언러닝` | Pages Router 습관의 잔재 → `unlearning.md`로 옮긴다 |

## 주기적으로 할 것

- **주 1회** — 이번 주 항목을 다시 읽고 설명 산출물 주제를 고른다
- **단계 종료 시** — 태그별로 집계한다. 한 태그에 몰려 있으면 그 영역을 다시 본다
- **`#언러닝` 항목** — `unlearning.md`로 옮기고 여기서는 지운다

### 7일차 (9/1 · S18 Route Handlers)
[상황]  웜업에서 "res.json() 을 두 번 호출하면 TypeError"를 정답으로 답한 직후,
        같은 세션 S18 예측에서 "request.json() 을 두 번 호출하면 빈 값"이라고 답함
[실제]  같은 TypeError. Response 든 Request 든 body 는 같은 스트림 규격이고
        메시지까지 동일하다 — "Body is unusable: Body has already been read"
[전제]  "이미 읽으면 비워져서 빈 값이 된다"고 기억하고 있었다.
        실제로는 비워지는 게 아니라 잠겨서(bodyUsed: true) 접근이 막히고 TypeError 가 난다.
        ※ 조수가 clone 설명 때 "스트림이 이미 비었으니까요"라고 쓴 표현이 오해를 만들었다.
          정확한 표현은 "소비되어 잠겼다"
[태그]  #서버실행 #관찰방법

주: 같은 패턴이 세 번째다.
    1단계 졸업시험 — "번들에 들어가는가"는 맞추고 "어디서 실행되는가"는 틀림
    오늘        — "res.json()"은 맞추고 "request.json()"은 틀림
    지식이 없는 게 아니라 문제 형태가 바뀌면 꺼내지 못한다.

[상황]  page.tsx 와 route.ts 가 같은 폴더에 있으면 "page.tsx 를 우선으로 잡는다"고 예측
[실제]  우선순위 없이 빌드 에러. 게다가 해당 라우트만이 아니라 앱 전체가 500 이 된다
[전제]  error.tsx 가 "가장 가까운 것이 잡는다"는 규칙을 라우트 충돌에도 유추 적용했다.
        경계 탐색(여러 후보 중 하나를 고름)과 라우트 등록(같은 URL 은 하나여야 함)은
        다른 문제다. 유추가 통하지 않는 지점
[태그]  #라우팅

### 6일차 (8/31 · S15·S16 웜업)
[상황]  body를 두 번 읽으면 "빈 값이 나온다"고 답. 서버가 쿠키의 HttpOnly 여부를 "알 수 있다"고 답
[실제]  TypeError가 발생한다. 서버는 알 수 없다 — 요청 Cookie 헤더에는 이름=값만 온다
[전제]  3일이 지나는 동안 복습을 하지 않았다. 실행 결과를 눈으로 보는 것만으로는
        3일을 못 넘긴다 — 본 것과 남는 것은 다르다
[태그]  #서버실행

주: 두 항목 모두 3일 전 실행 결과로 직접 확인한 것. 5일차 기록이 누락된 구간과 겹친다.

### 5일차 (8/28 · S15·S16)
[상황]  GET에 body를 넣으면 무시될 것으로 예측. 미들웨어 body 소비는 "반환값을 읽으면" 해결될 것으로 예측
[실제]  GET+body는 TypeError. 반환값은 같은 객체라 여전히 못 읽음 — 읽기 전에 clone() 해야 한다
[전제]  예전에 API를 호출했을 때 무시됐다고 기억하고 있었는데, 돌이켜보니
        try/catch를 안 넣었거나 async를 안 써서 에러를 못 본 것이었다.
        "예전에 그랬던 것 같다"는 기억이 잘못된 기대를 만들었다
[태그]  #서버실행

[상황]  Secure 속성이 "쿠키 접근을 막는다"고 답
[실제]  Secure는 HTTPS에서만 전송하도록 전송 채널을 제한. 접근 차단은 HttpOnly
[전제]  세 속성을 "쿠키를 보호하는 것들"로 뭉뚱그렸다. 각각 다른 공격을 막는다
[태그]  #서버실행

### 4일차 (8/26 · S5 · 졸업시험)
[상황]  졸업시험 문제1에서 Icon·format.ts를 누락하고 UserPanel을 잘못 포함.
        문제5에서 Table을 "클라이언트에서 실행"이라 답 (같은 시험 문제1에서는 같은 구조를 제외했음)
[실제]  import는 재귀로 따라가야 하고, prop으로 넘어온 것은 따라가지 않는다.
        "번들에 들어가는가"와 "어디서 실행되는가"는 같은 질문
[전제]  두 질문을 서로 다른 것으로 인식했다. 절차 1을 "번들 목록 만드는 도구"로만
        익혀서, 실행 위치를 묻는 형태로 나오면 절차를 꺼내지 않았다.
        절차는 알면서 적용 범위를 몰랐던 상태
[태그]  #rsc경계

### 3일차 (8/25 · S4 직렬화)
[상황]  date·map·set·promise를 "새로 생성하는 객체/함수라서" 실패로 예측
[실제]  넷 다 성공. 타입까지 보존되어 도착
[전제]  new 가 붙어 있어서 "직접 생성하는 것"이라 보고 plain object 와 다르게 취급했다.
        실제 기준은 new 여부가 아니라 "React 가 복원법을 아는 타입인가"
[태그]  #rsc경계

### 2일차
[상황]  prefetch를 끄면 클릭 시 서버 요청이 생기므로 template이 서버에서 재실행될 것이라 예측
[실제]  요청은 발생했지만 page(🔷)만 렌더링됨. template은 서버에서 실행 안 됨
[전제]  "재마운트 = 서버 재실행"이라고 생각했다. 실제로 재마운트는 클라이언트 층의 일이고, 서버는 클라이언트 전환 시 바뀌는 세그먼트만 렌더링한다
[태그]  #rsc경계

[상황]  template 카운터는 초기화되는데 console.log는 안 찍혀서 모순처럼 보였다
[실제]  서로 다른 층에서 일어난 일. 서버 로그는 서버 실행만 보여준다
[전제]  하나의 도구(터미널)로 모든 층의 동작을 관찰할 수 있다고 가정했다. 앞으로는 "이 현상은 어느 층인가"를 먼저 정하고 도구를 고를 것
[태그]  #관찰방법
