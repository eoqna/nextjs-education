# Next.js 학습 계획 설계

- **작성일:** 2026-08-14
- **기준 버전:** Next.js 16.3.1 (공식 문서 기준일 2026-08-10)
- **기간:** 15주 / 약 125시간
- **상태:** 확정

---

## 1. 배경과 목표

### 1.1 학습자 프로필

| 항목 | 내용 |
|---|---|
| React 경력 | 4년 |
| Next.js 심화 경험 | 없음 |
| TypeScript | 상시 사용 |
| SSR/SSG 프레임워크 | 경험 있음 (Pages Router 계열) |
| Node.js 백엔드 직접 작성 | **없음** |
| React Query / SWR | **미사용** |
| 가용 시간 | 주 6~10시간 |
| 실무 투입 시점 | 약 3~4개월 뒤 |

### 1.2 목표

**Claude Code가 작성한 Next.js 코드의 동작을 읽기 전에 예측할 수 있고, 남에게 설명할 수 있는 수준에 도달한다.**

"이해한다"가 아니라 **"예측한다"** 와 **"설명한다"** 를 목표로 잡은 것이 이 계획의 전제다. 읽고 이해하는 것과 보기 전에 예측하는 것은 다른 능력이며, 후자만이 코드 생성 도구를 쓰면서도 주도권을 유지하게 해준다.

최종 산출물로 간단한 사이드 프로젝트를 완성한다.

### 1.3 갭 분석

**보유:** TypeScript, 서버 렌더링/hydration 개념

**갭 1 — 서버 사이드 실행 경험 (큼)**
Node 백엔드를 직접 작성한 적이 없다면 요청/응답 라이프사이클, 쿠키·헤더 조작, 스트리밍, 에러 전파가 전부 새롭다. Next.js는 풀스택 프레임워크이므로 이것이 학습량의 절반을 차지한다.

**갭 2 — 캐싱 멘탈 모델 (완화됨)**
React Query/SWR 미경험으로 stale/revalidate/invalidate 사고방식이 없다. **다만 Next.js 16의 Cache Components 모델은 캐싱이 명시적 opt-in이므로 이 갭의 위험도가 크게 낮아졌다.** 구모델의 난이도 대부분은 "시키지도 않았는데 캐시됨"에서 왔는데, 신모델에는 그 함정이 없다. 지울 습관이 없다는 점에서 오히려 유리할 수 있다.

**리스크 — 언러닝**
Pages Router 계열 경험이 App Router에서 잘못된 예측을 만들어낸다. `getServerSideProps` / `getStaticProps` 반사신경이 RSC와 충돌한다. 이것이 1단계를 언러닝부터 시작하는 이유다.

## 2. 학습 방법론

### 2.1 채택안 — 예측-검증 루프

**Claude Code를 코드 생성기가 아니라 출제자이자 채점자로 사용한다.**

목표가 "예측과 설명"이므로 학습 루프를 그 능력에 정확히 맞춘다.

1. **예측 먼저** — 코드를 받거나 실행하기 **전에** 예측을 문서화한다
2. **실행/확인** — 그다음에 실제로 돌려보거나 문서를 확인한다
3. **틀린 지점만이 학습** — 맞춘 것은 넘어가고 틀린 것만 오답노트에 남긴다

여기에 **의도적 고장내기**를 결합한다. 캐싱과 프리렌더는 정상 동작을 관찰해서는 이해되지 않고, 직접 망가뜨려 증상을 겪어야 각인된다.

### 2.2 기각한 대안과 사유

**문서 순회형 (기각)**
공식문서를 순서대로 읽고 챕터마다 실습. 빠지는 개념은 없으나 **읽기는 수동적 활동이라 예측 능력이 길러지지 않는다.** 읽을 때는 이해한 것 같은데 코드를 보면 예측이 안 되는 현상이 문서 학습의 고질병이다. 또한 125시간 중 상당수가 당장 쓰지 않을 API 레퍼런스 소비에 들어간다.

→ **공식문서는 참조자료로 격하한다.** 처음부터 끝까지 읽지 않고, 예측을 검증할 때 해당 섹션만 펼친다.

**프로젝트 우선형 (부분 채택)**
바로 프로젝트를 시작하고 막힐 때마다 문서를 판다. 동기부여와 실전 맥락은 최고지만 **갭 2에 최악이다.** 캐싱과 프리렌더는 "안 막히면 안 배우는" 영역이고, 문제가 프로덕션에서야 드러나므로 그때까지 잘못된 멘탈 모델이 굳는다.

→ **4단계에서만 채택한다.** 앞 3단계가 방어선 역할을 한 뒤에 투입한다.

### 2.3 전체 구조

```
1단계  언러닝 + RSC 멘탈 모델   →  예측-검증 루프
2단계  서버 사이드 실행 (갭 1)  →  예측-검증 루프 + 의도적 고장내기
3단계  PPR + 명시적 캐싱 (갭 2) →  의도적 고장내기 중심
4단계  사이드 프로젝트          →  프로젝트 우선. 앞 3단계가 시험대에 오름
공식문서                        →  전 구간 참조자료
```

## 3. 학습 루프 메커니즘

### 3.1 세션 구조 (1회 1.5~2시간, 주 4~5회)

| 단계 | 시간 | 내용 |
|---|---|---|
| ① 웜업 예측 퀴즈 | 10분 | 지난 세션 + 오답노트에서 뽑은 스니펫 동작 맞히기 |
| ② 새 개념 **예측** | 15분 | 문서 읽기 **전에** 예제 코드를 보고 예측 작성 |
| ③ 문서 확인 | 30분 | 해당 문서 섹션을 읽고 예측과 대조 |
| ④ 실습 + **고장내기** | 40분 | 직접 작성 후 일부러 망가뜨려 동작 관찰 |
| ⑤ 오답노트 | 10분 | **틀린 것만** 기록 |

**②가 ③보다 앞에 온다는 것이 이 구조의 전부다.** 순서가 뒤집히면 문서 순회형으로 퇴화한다.

### 3.2 4문 예측 카드

모든 예측은 이 네 질문으로 통일한다. Next.js 이해의 거의 전부가 여기 들어간다.

```
① 어디서 실행되는가?          프리렌더(빌드) / 요청시 서버 / 클라이언트
② 정적 셸에 들어가는가?       셸에 포함 / Suspense 뒤에서 스트리밍
③ 클라이언트 번들에 포함되는가?  O / X   (이 import는? 이 변수는?)
④ 캐시된다면 lifetime은?      cacheLife 프로필은 무엇이고 무엇이 무효화하나?
                              (revalidateTag / updateTag / refresh 중 어느 것)
```

**질문을 매번 바꾸지 않는다.** 같은 네 질문을 100번 반복해야 반사적 판별이 자동화된다. 그 자동화된 상태가 곧 "예측할 수 있는 수준"이다.

②번이 Next.js 16 기준의 핵심 질문이다. 이전 모델에서는 "언제 다시 실행되는가"가 핵심이었으나, PPR이 기본이 된 지금은 정적 셸 포함 여부가 렌더링 동작을 결정한다.

### 3.3 Claude Code 사용 5조

"코드는 Claude가 쓰는데 나는 모르는 상태"를 막는 방어선. `CLAUDE.md`에 기재하여 도구가 강제하게 한다.

1. **요청 전에 내 설계를 먼저 적는다** — "서버 컴포넌트 1개 + 클라이언트 컴포넌트 1개, 데이터는 서버에서 fetch, 폼은 Server Action" 수준으로
2. **받은 코드를 읽기 전에 4문 카드를 채운다** — 스크롤을 내리기 전에
3. **설명을 요구하기 전에 내 설명을 먼저 말한다** — 그다음 "내 설명 어디가 틀렸어?"라고 묻는다. 순서가 반대면 학습이 아니라 받아쓰기다
4. **막히면 답 대신 힌트를 요청한다** — "답 말고 어느 문서 어느 섹션 볼지만 알려줘"
5. **세션 끝에 역할을 바꾼다** — Claude Code에게 오늘 배운 내용으로 예측 퀴즈를 출제시킨다. 답은 다음 세션 웜업에서 확인

### 3.4 오답노트

단순 실수(오타, API 이름 착각)는 **기록하지 않는다.** 기록 대상은 멘탈 모델 오류뿐이며 형식을 지킨다.

```
[상황]  무엇을 예측했나
[실제]  실제로는 어떻게 동작했나
[전제]  내가 왜 그렇게 예측했나        ← 가장 중요한 줄
[태그]  #rsc경계 #캐싱 #프리렌더 #라우팅 #언러닝
```

`[전제]` 줄이 핵심이다. 틀린 답이 아니라 **틀린 전제**를 고쳐야 재발하지 않는다. `#언러닝` 태그 항목은 Pages Router 습관의 잔재이므로 별도로 모아 주기적으로 재점검한다.

## 4. 커리큘럼

총 15주 / 약 125시간.

### 4.1 1단계 · 언러닝 + RSC 멘탈 모델 (3주, ~25h)

> **목표:** 임의의 컴포넌트 트리를 보고 어디까지가 클라이언트 번들인지 그림으로 그릴 수 있다.

- App Router 파일 규약 (`layout` / `page` / `loading` / `error` / `not-found` / `route`) — 빠르게 통과
- 서버 컴포넌트가 **기본값**이라는 것, `async` 컴포넌트
- `'use client'`의 정확한 의미 — "이 파일이 클라이언트"가 아니라 **"여기부터 아래 import 그래프 전체가 클라이언트"** 라는 경계 선언
- **직렬화 경계** — props로 넘길 수 있는 것과 없는 것 (함수, Date, Map, 클래스 인스턴스)
- **컴포지션 패턴** — `children`으로 서버 컴포넌트를 클라이언트 컴포넌트 *안에* 넣기. 1단계 최난관이며, 여기서 막히면 앱 전체가 `'use client'`로 도배된다
- **`await params` / `await searchParams`** — Next.js 16에서 동기 접근은 제거되었다. 검색으로 나오는 대부분의 글이 동기 코드이므로 혼란의 1순위 원인
- 언러닝 대조표 작성 — `getServerSideProps` / `getStaticProps` 사고가 각각 무엇으로 대체되는가

**고장내기:** 서버 컴포넌트에서 `useState` 사용 · 클라이언트 컴포넌트에 함수 prop 전달 · 서버 전용 라이브러리를 클라이언트에서 import

**졸업 시험:** 컴포넌트 트리를 주고 클라이언트 번들 경계를 손으로 그리기

### 4.2 2단계 · 서버 사이드 실행 (4주, ~35h) — 갭 1

> **목표:** 인증이 붙은 CRUD를 문서 최소 참조로 구현할 수 있다.

Node 백엔드 경험이 없으므로 **앞부분에 웹 표준 `Request`/`Response`, 쿠키·헤더 기초를 짧게 보강**하고 들어간다. 이를 건너뛰면 Route Handlers가 계속 마법처럼 느껴진다.

- 서버에서의 데이터 fetch, `async` 컴포넌트
- **Route Handlers** — 웹 표준 `Request`/`Response` 기반
- **Server Actions** — 폼, `useActionState`, `useFormStatus`, `redirect`
- **런타임 API (전부 비동기)** — `await cookies()`, `await headers()`, `await draftMode()`
- **`proxy.ts`** — Next.js 16에서 `middleware.ts`를 대체. Node.js 런타임에서 실행되며 `middleware.ts`는 deprecated (Edge 용도로만 잔존)
- **스트리밍 기초** — `Suspense`, `loading.tsx`. 본격적인 경계 설계는 3단계로 이월
- **에러 경계 2종** — 라우트 단위 `error.tsx`, 컴포넌트 단위 `catchError()`
- **환경변수** — `NEXT_PUBLIC_` 접두사의 실제 의미 (번들에 문자열로 인라인됨)

**고장내기:** 클라이언트에서 서버 전용 env 접근 · Server Action에서 권한 체크를 제거하고 직접 호출 (보안 감각) · `await` 누락

**졸업 시험:** 인증 붙은 CRUD를 문서 최소 참조로 구현

### 4.3 3단계 · PPR + 명시적 캐싱 (3주, ~25h) — 갭 2

> **목표:** 임의의 페이지 코드를 보고 정적 셸 / 캐시된 부분 / 스트리밍되는 부분을 색칠해서 그릴 수 있다. dev 오버레이의 도움 없이.

**첫날 `cacheComponents: true`를 켜고 시작한다.** 끄고 배운 뒤 나중에 켜면 두 번 배우게 된다.

#### 3-1주 · 프리렌더를 막는 것들

이 주차의 백본은 **dev 오버레이 insight를 일부러 하나씩 유발시키는 것**이다.

| 유발할 insight | 유발 방법 |
|---|---|
| `blocking-route` | `await cookies()` 를 `Suspense` 없이 사용 |
| `blocking-prerender-random` | `Math.random()` |
| `blocking-prerender-current-time` | `Date.now()` |
| `blocking-prerender-crypto` | `crypto.randomUUID()` |

각각에 대해 오버레이가 제시하는 **세 가지 수정법(캐시하기 / `Suspense`로 감싸기 / 라우트 opt-out)을 모두 적용**하고 결과 차이를 관찰한다.

- `connection()` 이 왜 필요한가 — 요청마다 고유한 값이 필요할 때
- 반대로 module import, `fs.readFileSync`, 순수 계산은 왜 자동으로 프리렌더되는가
- 요청과 무관한 리소스는 모듈 스코프에서 한 번만 읽는 패턴

#### 3-2주 · `use cache` 3종 세트

- data-level(함수 캐싱) vs UI-level(컴포넌트·페이지 캐싱)
- **캐시 키가 자동 생성된다** — 인자와 클로저로 잡힌 값이 키에 포함된다. 여기서 직렬화 제약이 재등장 (1단계와 연결)
- `cacheLife` 의 세 축: `stale` / `revalidate` / `expire`. 모든 캐시 디렉티브에 `cacheLife`를 짝지어 쓰는 것이 권장사항
- `cacheTag` 로 태깅

**저장 위치가 다른 세 변종 — 3-2주의 핵심**

| 변종 | 저장 위치 | 특성 |
|---|---|---|
| `use cache` | 서버 인스턴스 메모리 | 서버리스에서는 휘발성 |
| `use cache: private` | 브라우저 | 쿠키/헤더를 읽어도 캐시 가능 |
| `use cache: remote` | 공유 durable 스토어 | 네트워크 왕복 비용, hit rate가 높아야 이득 |

**무효화 3종**

| API | 사용 위치 | 동작 |
|---|---|---|
| `revalidateTag(tag, profile)` | 어디서나 | 태그된 캐시 무효화 + SWR. 2번째 인자(cacheLife 프로필) 필수화됨 |
| `updateTag(tag)` | Server Action 전용 | read-your-writes — 변경이 즉시 반영 |
| `refresh()` | Server Action 전용 | **캐시를 건드리지 않고** 캐시되지 않은 데이터만 갱신 |

- 런타임 값을 추출해 캐시 함수의 인자로 넘기는 패턴
- 모든 캐시 스토어는 배포 단위로 스코프됨 — 새 배포는 빈 캐시로 시작 (캐시 키에 build id 포함)

**실습:** 같은 데이터를 4가지 방식(캐시 없음 / `use cache` / `private` / `remote`)으로 두고 새로고침·네비게이션·재배포 시 동작 차이를 관찰

#### 3-3주 · 정적 셸 최대화 + 구모델 대조

- **`await`를 트리 아래로 내리기** — layout에서 `await params` 하지 말고 params promise를 자식에게 넘겨 그 안에서 await한다. Next.js 16 설계 감각의 정수이며 이 단계의 결론
- Suspense 경계 긋기
- Partial Prefetching, `<Link prefetch>`, App Shell 개념
- ISR with Cache Components, `generateStaticParams`
- **`<Activity>`** — `cacheComponents` 활성화 시 네비게이션에서 컴포넌트 state가 보존된다. 드롭다운·다이얼로그가 언마운트 전제와 다르게 동작하므로 주의
- 봇/크롤러는 셸을 건너뛰고 전체를 동적 렌더링한다는 점

**마지막 1세션 · 구모델 대조**
플래그를 끄고 같은 앱을 구모델로 재구성한다.

- `fetch` 옵션 (`cache: 'force-cache'`, `next.revalidate`, `next.tags`) — 기본적으로 캐시되지 않음
- `unstable_cache` — non-fetch 함수용
- Route segment config — `dynamic`, `revalidate`, `fetchCache`
- React `cache` 로 렌더 패스 내 중복 제거
- `revalidatePath` / `revalidateTag`

그리고 **"신모델의 X는 구모델에서 Y가 자동으로 하던 것"** 매핑표를 직접 작성한다. 이 표 한 장이 3~4개월 뒤 구버전 프로젝트에 투입됐을 때의 보험이다.

**졸업 시험:** 페이지 코드를 주고 정적 셸 / 캐시 / 스트리밍 영역 색칠하기

### 4.4 4단계 · 사이드 프로젝트 (5주, ~40h)

앞 3단계가 시험대에 오른다. 여기서 새로 만나는 것들:

- 인증, DB 연동, 배포
- 이미지·폰트 최적화, 메타데이터/SEO
- 성능 측정 — 번들 분석, 무엇이 클라이언트로 넘어갔는지 실측

**규칙:** 새 기능을 시작하기 전에 반드시 4문 예측 카드로 설계를 먼저 적는다. 이 규칙을 놓으면 프로젝트 우선형으로 퇴화한다.

**Next.js DevTools MCP를 여기서 붙인다.** Claude Code에 Next.js의 라우팅·캐싱·렌더링 동작 지식과 서버/브라우저 통합 로그가 연결된다. **1~3단계에서는 붙이지 않는다** — 스스로 진단해야 할 것을 도구가 대신 진단해버린다.

**졸업 시험:** 프로젝트의 임의 파일을 열어 4문 카드를 즉답

## 5. 검증 체계

세 층위로 확인한다. 하나만으로는 자기기만이 쉽다.

**① 세션 단위 — 예측 적중률**

**② 주 단위 — 설명 산출물**
500~800자. 주제는 그 주의 오답노트에서 선정한다 (틀린 것이 곧 설명할 가치가 있는 것). **남에게 설명하는 톤으로 쓴다.** 쓰다가 막히면 아직 이해하지 못한 것이며, 그 지점이 다음 주 학습 항목이 된다. 총 15편.

**③ 단계 단위 — 졸업 시험**
각 단계의 졸업 시험(4장 참조)은 Claude Code에게 출제를 맡긴다. 배운 범위를 알려주고 문제만 받으며, 답은 스스로 작성한 뒤 채점을 요청한다.

**`labs/`에서 고장낸 코드를 지우지 않는다.** 나중에 같은 증상을 만났을 때 돌아올 참조점이 된다.

## 7. 버전 고정

**Next.js 16.3.x로 고정하고, 해당 버전 공식 문서만 참조한다.**

검색으로 나오는 블로그 글의 상당수가 Next.js 14/15 기준이며, 학습 중 혼란의 가장 큰 원인이 된다. 특히 다음 항목들이 구버전 자료와 정면으로 충돌한다.

| 항목 | 구버전 자료 | v16 실제 |
|---|---|---|
| 캐싱 모델 | 암묵적 4레이어 | **명시적 opt-in (`use cache`)** |
| 렌더링 | static이냐 dynamic이냐 이분법 | **PPR이 기본, 한 페이지에 공존** |
| `params` / `searchParams` | 동기 접근 | **`await` 필수** |
| `cookies()` / `headers()` | 동기 접근 | **`await` 필수** |
| 요청 인터셉트 | `middleware.ts` | **`proxy.ts`** (Node.js 런타임) |
| 태그 무효화 | `revalidateTag(tag)` | **`revalidateTag(tag, profile)`** + `updateTag` / `refresh` 분화 |
| PPR 활성화 | `experimental.ppr` | **제거됨 → `cacheComponents`로 통합** |
| 번들러 | webpack | **Turbopack 기본** |
| 린트 | `next lint` | **제거됨** (ESLint/Biome 직접 사용) |

기타 v16 변경사항: 병렬 라우트에 `default.js` 필수, `next/image` 기본값 변경(`qualities`, `minimumCacheTTL`, `imageSizes`), `serverRuntimeConfig`/`publicRuntimeConfig` 제거, AMP 지원 제거, Node.js 20.9+ / TypeScript 5.1+ 요구.

## 8. 리스크와 대응

**리스크 1 — 예측 단계를 건너뛰게 됨**
가장 큰 실패 모드. 답부터 보고 싶은 유혹이 크다.
→ `CLAUDE.md`로 도구가 강제하게 한다. 오답노트가 며칠째 비어 있으면 예측을 안 하고 있다는 신호로 간주한다.

**리스크 2 — 학습 기간 중 Next.js 마이너 버전 상승**
16.4 등이 나오면 일부 API가 바뀔 수 있다.
→ 학습 중에는 버전을 올리지 않는다. 4단계 시작 시점에만 한 번 재검토한다.

**리스크 3 — 실무 프로젝트가 구모델일 가능성**
3~4개월 뒤 투입될 프로젝트가 Next.js 14/15 또는 `cacheComponents` 미적용일 확률이 상당하다.
→ 3-3주의 구모델 대조 세션과 `cache-model-map.md`가 이 리스크의 대응책이다. 명시적 모델을 먼저 배운 뒤 "구모델은 이것이 자동으로 일어나는 버전"으로 매핑하는 순서가, 그 반대보다 학습 효율이 높다.

**리스크 4 — 3단계 난이도 과소평가**
캐싱 부담은 줄었지만 **"Suspense 경계를 어디에 그을 것인가"** 라는 새로운 난관으로 옮겨갔다.
→ 3주로 부족하면 4단계에서 1주를 빌려온다. 사이드 프로젝트 규모를 줄이는 것이 3단계를 건너뛰는 것보다 낫다.
